# Независимое подтверждение индекса дома — задача #5

Проверено 19.10.2026 на main `eaf31f7ed41f2cb977cc0e610f42f35378828a92` (после PR #13).
Статус: **blocked_external_dependency**. Автоматизация вне каталога не включена.

## Почему текущих данных недостаточно

Geoapify возвращает геокодирование, но не независимое доказательство обслуживания дома данным почтовым отделением. `confidence=1`, `building`, совпавшие координаты, шесть цифр, существующее ОПС и совпадение двух геокодеров недостаточны. Геокодеры могут использовать общий исходный справочник. В ответе текущего адаптера нет признака актуальности именно связи дом → индекс; возраст HTTP-ответа не равен возрасту данных. Сохранённый официальный адрес ФНС пригоден для эталона конкретного дома, но расширение каталога этим корпусом уничтожит независимость оценки.

В core найден отдельный дефект: ключ дедупликации не включал confidence/resultType. Для одинаковых адреса и индекса последний ответ заменял предыдущий. Последовательность `street → building` либо `0.8 → 1` могла дать confirmed, обратный порядок — ambiguous. Это воспроизводится и после применения каталога РФ. Минимальное исправление сохраняет различающееся доказательство: противоречивые записи требуют выбора при любом порядке. Полностью идентичные записи по-прежнему объединяются.

## Конкретная недостающая зависимость

Нужен оплаченный доступ к DaData **Clean**, API token + secret, и серверная точка исполнения с утверждённой политикой передачи адресов. Документация не поддерживает Clean из браузерного JavaScript из-за секретного ключа. Общий secret нельзя встраивать в ZIP или content script. В текущем расширении есть только привилегированный Geoapify key; серверного адаптера Clean и его безопасной конфигурации нет. В доступном локальном окружении GEOAPIFY_API_KEY, DADATA_API_KEY и DADATA_SECRET_KEY отсутствуют (проверено наличие, значения не читались в вывод).

Рекомендуемый следующий шаг: сначала отдельный серверный эксперимент, без изменения разрешений расширения и автозаполнения. Запрашивать Clean по исходным компонентам **без индекса Geoapify или эталона ФНС**, чтобы не подсказывать ожидаемый ответ. Сохранить безопасные ответы публичного корпуса, время запроса, версию источника/даты данных, если доступны, и причины отказа. HTTP 200 не доказывает свежесть. Если провайдер не даёт достаточной информации об актуальности почтовых назначений, согласовать SLA/период обновления либо получить первичное подтверждение Почты; до этого автоматизацию не включать.

## Условия будущего разрешения автоподтверждения

1. Единственная однозначная связь с точным домом: регион и административная иерархия, city/settlement, тип улицы, номер, литера, корпус, строение; никакого подбора соседнего дома. Неоднозначные города без региона — ручной выбор. Федеральные города и посёлки требуют явного, протестированного преобразования, не `city || settlement` без проверки иерархии.
2. Валидный шестизначный индекс, стабильный house ID, актуальность дома, отсутствие альтернатив и неразобранных частей. Clean qc=0 и qc_house=2 — необходимые фильтры эксперимента, а не сертификат индекса. qc_complete=5 означает отсутствие квартиры и не является ошибкой house-level проверки; qc_complete=8 (абонентский ящик / до востребования) не доказывает индекс дома.
3. Подтверждение связано с исходным addressKey, house ID, индексом и источником; не переносится на изменённый адрес или другой индекс. Несогласие источников, устаревшие/неизвестные даты, пустые и повреждённые ответы, 401/403/429, timeout — ручной путь или явная ошибка, без автоматического fallback на Geoapify. Отозванное подтверждение не оживает из кэша; TTL результата ограничить сроком доказательства, а запоздавший ответ отбрасывать средствами FormSession.
4. До включения — контрактные тесты ошибочных индексов, альтернативных домов/регионов, корпуса/строения, удалённых и переименованных объектов, старых данных, malformed payload и сетевых ошибок. Два ответа из одного upstream не считать независимыми голосами. Сначала подтверждать только согласованный индекс; разрешение исправлять расхождение требует отдельного доказательства и тестов.

## Выполненная проверка и критерии выпуска

`npm test -- tests/core/address-policy.test.ts tests/adapters/geoapify.test.ts tests/adapters/russia-independent-policy.test.ts`: 55 passed. Новый тест прогоняет все 100 независимых адресов в трёх сценариях: неправильный индекс при точном доме, конфликт индексов, ответ для другого корпуса дома (модель устаревшей привязки, а не реальная проверка возраста данных). Все 300 ответов требуют ручного выбора. Существующая проверка идеальных ответов: 0/100 confirmed, 100/100 ambiguous. Итого 400 синтетических сценариев; это проверка защиты, **не живая оценка точности**. Запросов Geoapify/Clean/Почты — 0.

После появления зависимости прогнать замороженную политику через production application path на независимом корпусе: ≥100 адресов, ≥10 регионов, ≤20% на регион, ≥90% правильных автоматических подтверждений, 0 неправильных, 0 ошибок. Сохранить воспроизводимый отчёт с исходным SHA и происхождением ответов. Если корпус используется для настройки новой политики, подготовить дополнительный нетронутый holdout. Текущий benchmark использует только Geoapify: перед будущим живым замером подключить тот же проверяющий адаптер, что и в продукте. Ни новый корпус, ни его индексы не добавлены в каталог; gate остаётся закрыт, задача #5 не решена.
